# Credential examples and verification results

Open the [Credential Builder with the EUDI PID example](http://127.0.0.1:4180/apps/builder/?example=eudi-pid-sd-jwt). Pick an example under **Credential examples with sources**. The panel shows its format, provenance and ODRL condition. **Run example check** sends the current JSON to the server. **Load counterexample** replaces one field in the published or adapted sample so you can run the same rule again.

The examples share the Guard's Basic ODRL compiler. They compare one top-level JSON value and return an HTTP 200 JSON boolean. They use a separate read-only route, `POST /examples/credentials/<id>/check`, with the same `{"data": {...}}` request body as an ODRL Guard endpoint. The fixture catalog is available at `GET /examples/credentials.json`. Saved Guard rules and endpoints are independent of the example routes.

The HTTP tests also removed the checked field and supplied a value of the wrong JSON type. All ten variants returned `false`. A `true` result means that the configured field comparison succeeded. In a deployed verifier, trusted claim extraction, proof validation and issuer trust must run before using these facts to allow a request.

## Separate raw-vector checks

These offline checks were run separately from the Builder and illustrate which work a format adapter must do before handing claims to a policy.

The [signed Guard demos](../signed/README.md) now run issuer verification before ODRL on separate endpoints. This Builder catalog still runs field comparisons on JSON inputs.

- **EUDI mdoc.** The COSE `issuerAuth` ES256 signature verified against the embedded development certificate. All 20 issuer-signed item digests matched the signed Mobile Security Object. A modified signed payload failed signature verification, and changing the `issuing_country` item failed its digest check. This establishes integrity under the embedded key. Issuer trust, status and device authentication require separate checks. [EUDI reference test vector](https://github.com/eu-digital-identity-wallet/eudi-lib-jvm-openid4vp-kt/blob/8897d4324a8e34cc5de90b4eadffc656517a4924/src/test/resources/example/mso_mdoc_pid-issuersigned.txt)
- **EUDI development SD-JWT.** A separate, older fixture from the EUDI reference library passed ES256 signature verification against its embedded certificate and all 23 disclosure digest checks. Modifying the signed payload or a disclosure broke the corresponding check. The token expired on 2025-01-01. The exercise establishes test-vector integrity under the embedded key. [EUDI SD-JWT library `pid1` fixture](https://github.com/eu-digital-identity-wallet/eudi-lib-jvm-sdjwt-kt/blob/68db743eb40a6c66bf4668560976206dc9cb0422/src/test/kotlin/eu/europa/ec/eudi/sdjwt/PidDevVerificationTest.kt)
- **IETF SD-JWT+KB.** The issuer ES256 signature verified against the published test key and the holder signature against `cnf.jwk`. Three disclosure digests, `sd_hash`, and the fixture's audience and nonce matched. Changing the signed `vct` broke the issuer signature, and changing the age disclosure broke its digest and `sd_hash`. The fixed audience and nonce belong to the published test scenario. [RFC 9901 Appendix A.3 and A.5](https://www.rfc-editor.org/rfc/rfc9901.html#appendix-A.3)
- **Historical X.509.** OpenSSL verified the test chain with the example CA at 2005-02-06 using `-attime 1107648000 -auth_level 0 -check_ss_sig`. Adding the example CRL rejected the certificate as revoked. Verification on 2026-11-06 failed because both the CA and leaf had expired. This explains why a matching serial number in the Builder is independent of certificate validity. [RFC 5280 Appendix C](https://www.rfc-editor.org/rfc/rfc5280.html#appendix-C)
